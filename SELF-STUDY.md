## Результати експериментів

### 1. Експеримент із XSS-атакою (Урок №1)
При додаванні товару з назвою `<script>alert(1)</script>` скрипт не виконався у браузері.
* **Перегляд коду сторінки (Ctrl+U):** `<script>` перетворилося на `&lt;script&gt;alert(1)&lt;/script&gt;`.
* **Висновок:** Django DTL за замовчуванням автоматично екранує всі змінні, що запобігає XSS-вразливостям.

### 2. Експеримент з DEBUG = False (Урок №4)
При зміні `DEBUG = False` у `settings.py` таблиця та меню втратили стилізацію CSS (404/500 static file error).
* **Пояснення:** У режимі розробки Django роздає статичні файли самостійно. У продакшн-режимі (`DEBUG=False`) ця функціональність вимикається, адже цим має займатися веб-сервер (Nginx/WhiteNoise).

### 3. Експеримент із CSRF-захистом (Урок №5)
При вилученні прихованого поля `csrfmiddlewaretoken` з форми через DevTools та відправці POST-запиту отримати помилку:
`403 Forbidden: CSRF verification failed. Request aborted.`

#### Чому CSRF-запит було відхилено (пояснення):
CSRF (Cross-Site Request Forgery) — це атака, при якій зловмисник змушує браузер жертви виконати небажану дію на захищеному сайті. Django захищається від цього за допомогою порівняння двох секретних ключів: токена в Cookie браузера та прихованого токена у POST-формі. Оскільки приховане поле з форми було вилучено, сервер виявив невідповідність між токенами і негайно заблокував запит як потенційно шкідливий.
